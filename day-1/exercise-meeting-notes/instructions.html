Meet the agent: from a messy note to a diagram and an ADR

Participant guide — one folder, one note, two diagrams, one draft ADR

This page converts the exercise brief and its sibling source files into a single self-contained guide. You will work from a messy meeting note about customer-data sync at NorthGrove Foods, use the ADR template in the same folder, and direct the agent to produce reviewed outputs without hand-writing diagram syntax or ADR structure yourself.

  • diagrams.md with a current-state context diagram and nightly-sync sequence diagram
  • adr-001-customer-data-sync.md drafted from the note and verified against the source

Setup

Open the folder in VS Code and switch Copilot Chat from Ask to Agent. This exercise assumes the working folder is the one containing instructions.md, meeting-note.md, and adr-template.md.

Folder: day-1/exercise-meeting-notes
Chat mode: Agent

Source materials in this folder

The exercise revolves around two inputs and one instruction file. Read them like an architect, not a stenographer: separate facts from opinions, tensions from decisions, and missing data from actual constraints.

  • meeting-note.md — unreviewed notes from a discussion on synchronizing customer master data between CustomerHub, ERP EU, and ERP Americas
  • adr-template.md — the structure the draft ADR must follow, including status, context, decision, consequences, alternatives, and open questions
  • instructions.md — the original markdown brief now represented by this HTML page

What the note clearly contains: two ERP instances, a nightly CSV-over-SFTP sync, a recurring failure on the Americas load script, disagreement over required latency, three architecture options, a privacy concern, and two explicit follow-ups that were not completed.

Why this is a good agent exercise

The note is messy on purpose. It contains contradictions, missing numbers, implied bias, and unfinished follow-ups. That forces you to direct the agent to distinguish supported claims from assumptions instead of treating generated text as ground truth.

Step 1 — Summarize and question

The first task is extraction, not interpretation. The summary must split the note into two buckets: facts that the note actually states, and unresolved items that somebody could act on.

Read @file:meeting-note.md. Create summary.md with two sections:
1. "What we know" — the facts stated in the note, as bullets.
2. "Open questions" — everything unresolved, ambiguous, or promised
   but not delivered, each as a question someone could act on.
Do not invent information that is not in the note.

Check yourself after the agent responds:

  • Did it capture the disagreement between Tomás and Rachel as unresolved, rather than choosing a winner?
  • Did it keep the missing record counts as unknown instead of estimating them?
  • Did it avoid turning "leaning iPaaS" into a final decision?

Step 2 — Create the diagrams

Now move from bullet facts to visual structure. The diagrams should show only systems that the meeting note actually names. The first is a current-state context view; the second traces the nightly sync and its failure point.

From @file:meeting-note.md, create diagrams.md containing two Mermaid diagrams:
1. A context diagram of the CURRENT state: systems involved and how
   customer data flows between them today (include the failing parts).
2. A sequence diagram of today's nightly sync, from CustomerHub to
   both ERP systems, including the failure point on the Americas side.
Only include systems actually named in the note. Add a one-line caption
under each diagram.
If Mermaid preview shows an error

Open diagrams.md in preview. If Mermaid fails to render, paste the exact error text back into the chat and ask the agent to fix only the diagram syntax. That keeps the repair narrow and fast.

What a good context diagram should reveal:

  • The current design is batch-oriented, not event-driven.
  • ERP Americas has an unreliable downstream script and unclear ownership.
  • The pain is not only technical failure but also stale data and reconciliation effort.

Step 3 — Draft the ADR

Use the note plus the provided template to draft the middleware decision record. The critical test here is status discipline: the note suggests a direction, but it does not show board approval or a final decision.

Using @file:meeting-note.md and the structure in @file:adr-template.md, draft
adr-001-customer-data-sync.md for the middleware decision (iPaaS vs
point-to-point APIs vs event broker). Choose the Status honestly based
on what the note actually says. Put anything unresolved into Open
questions with an owner where the note names one.

Status sanity check: the note says the room is leaning toward iPaaS and that Devon should draft the decision properly for the architecture board. That supports Proposed, not Accepted, unless the agent can point to a stronger statement in the note.

What belongs in the ADR and what does not
  • Include the conflicting latency expectations because they shape the decision.
  • Include privacy follow-up as an open question because Legal raised it without specifics.
  • Do not add implementation details that the note never mentions, such as exact products, queues, schemas, or SLAs.

Step 4 — Verify before you trust

This is the most important step in the exercise. Ask the agent to review its own output against the original note, identify unsupported claims, and then repair the files so every assertion is either sourced or explicitly marked as an assumption.

Review @file:adr-001-customer-data-sync.md and @file:diagrams.md against
@file:meeting-note.md. List every claim that is NOT directly supported by
the note — invented details, opinions promoted to facts, or missing
caveats. Then fix the files so every claim is either supported or
clearly marked as an assumption.

Typical hallucinations to look for:

  • Invented data volumes or change rates
  • Assumed legal constraints beyond the note's brief warning
  • An asserted decision in favor of iPaaS
  • Named systems or teams not mentioned in the note

Done criteria

You are done when the generated files exist, the diagrams render, and the ADR plus diagrams survive a source-grounded review.

✔ Item What to verify
☐ summary.md Facts and open questions are separated cleanly
☐ diagrams.md Two Mermaid diagrams render and only use named systems
☐ adr-001-customer-data-sync.md Status is honest and unresolved items remain unresolved
☐ Verification pass Unsupported claims were listed and corrected
Optional extension if you finish early

Ask the agent for a diagram of the proposed iPaaS option, clearly labeled as a proposal, or generate user stories grouped by persona from the note.

Create a third Mermaid diagram in @file:diagrams.md that shows the PROPOSED
iPaaS option as a future-state view. Label it clearly as proposal, not
current state, and only include behaviors justified by @file:meeting-note.md.

Appendix — Embedded source files

adr-template.md

# ADR-NNN: <short title of the decision>

**Status:** Proposed | Accepted | Superseded
**Date:** <YYYY-MM-DD>
**Deciders:** <who is accountable for this decision>

## Context

<What situation forces this decision? Facts only — every statement here should be traceable to a source (meeting note, requirement, measurement). 3–6 sentences.>

## Decision

<The decision, stated in one or two sentences, active voice: "We will …". If not yet decided, state the leading option and keep Status = Proposed.>

## Consequences

<What becomes easier, what becomes harder, what new obligations appear (cost, operations, skills, vendor lock-in). Include negative consequences honestly.>

## Alternatives considered

<For each rejected option: one line on what it was and one line on why it lost.>

## Open questions

<Anything that must be answered before or shortly after this decision is final. Assign an owner where known.>

meeting-note.md

# Meeting notes — Customer data sync, ERP EU / ERP Americas (draft, unreviewed)

**Date:** March 11 — **Taken by:** Jonas (sorry, typing fast, gaps everywhere)
**Attendees:** Marta (EA), Priya (Data), Tomás (ERP EU), Rachel (ERP Americas), Devon (Integration), Karim (CRM), (Legal joined late, left early)

---

Context recap from Marta: NorthGrove Foods runs two ERP instances since the Meridian acquisition — **NG-ERP-EU** (S/4HANA, Frankfurt) and **NG-ERP-AM** (older ECC, hosted in Ohio, migration "someday"). Customer master data lives in **CustomerHub** (our CRM) but both ERPs keep their own copies. Same customer exists 2–3 times with different IDs. Finance reconciliation eats days every quarter close.

Current state (Devon): nightly CSV export from CustomerHub → SFTP → custom load scripts on each ERP. The Americas load script fails "maybe once a week", nobody owns it since Stefan left. EU side mostly OK but 24h delay causes the credit-limit issue Tomás keeps raising.

Tomás: sales orders get blocked on stale credit limits. For him **near real-time sync is a must**, said "if a customer is updated in CustomerHub, ERP should know within minutes."

Rachel: pushed back — for Americas, **nightly batch is fine**, finance only needs it for month-end anyway. "Let's not gold-plate this." (Not resolved — parking lot.)

Volume question came up — Karim didn't have numbers, said "it's a lot of records, especially after Meridian". **TODO: Karim to pull actual record counts and change rates.** (didn't happen yet)

Options on the table (Devon whiteboarded, photo lost, from memory):

1. **iPaaS** — use the integration platform we already license for the e-invoicing flows. Devon likes it: monitoring, retries, connectors for both SAP and CustomerHub out of the box. Concern: per-connection licensing cost, and the platform team is a bottleneck (6-week lead time for new flows??)
2. **Point-to-point APIs** — CustomerHub webhooks calling ERP APIs directly. Cheapest to start, Tomás's team could build the EU side themselves. Marta worried this recreates the spaghetti we're trying to kill.
3. **Event broker** — publish customer-changed events, both ERPs (and future consumers) subscribe. Priya's favorite, "aligns with the platform strategy". Nobody in the room has run one in production. Ops question totally open.

Priya mentioned the **MDM tool her team is piloting** — might become the golden record for customers "eventually"?? Unclear if it's in scope for this. Marta: "don't couple this project to the pilot." Left it there.

Legal (before dropping off): reminded everyone customer data is personal data, "there are rules about customer data crossing regions, check with privacy office before you move anything." No specifics given. **TODO: someone to follow up with privacy office** (no owner assigned…)
