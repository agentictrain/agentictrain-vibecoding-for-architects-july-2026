The Hello World Ladder

One task, five prompts — Participant guide

In this exercise you will build the same thing five times: a "hello world" page in HTML. What changes at each step is not the task but how you ask for it — from the laziest possible one-liner to a prompt engineered with evidence-backed best practices. Because the task is constant, every difference you see in the output is caused by the prompt. That's the whole lesson.

What you will do:

  1. Fire a naive one-shot prompt and inspect what the agent decides on your behalf.
  2. Run the same prompt in Plan mode and see what a planning step alone buys you.
  3. Use a structured prompt written by a human, with rules for the plan.
  4. Ask the agent to rewrite that prompt itself (meta-prompting), then run the improved version.
  5. Optimize the prompt with a machine-readable spec of best practices and compare the result against every previous step.

How to use this guide

  • Code blocks (gray background, fixed-width font) are prompts to copy into the Copilot chat. Copy them as-is with the Copy button.
  • Work in a fresh, empty folder per step (e.g. step1/, step2/…) so the results don't contaminate each other and you can diff them at the end.
  • Start a new chat session per step — otherwise the agent remembers the previous step and the comparison is no longer fair.
  • The blue collapsible boxes are optional extras explaining the technique behind each step. The exercise works without opening them; if you're curious, click and they expand (on wide screens, in the right margin).
  • The yellow boxes are questions to discuss — there is no single right answer.
  • After each step, fill in your row of the comparison table while the result is fresh.

Step 1 — Naive lazy one-shot

This is the prompt most people write on day one. Paste it in agent mode (not Plan mode), press enter, and touch nothing until it finishes:

write a great hello world app in html

When it's done, check the result: open the HTML file in a browser and look at what you got. Then look at what you didn't get:

  • Did the agent ask you a single question before building?
  • What did "great" turn out to mean? Who decided that — you or the model?
  • Does the file pull external resources (CDNs, fonts)? Would it work offline?
  • Did anything verify that the page actually works?
Why one-shot output is mediocre by design

Your prompt specified almost nothing, so the model filled every gap with the statistically average choice. Research identifies underspecification as a primary driver of output variance: the less you pin down, the more you get the average of the internet. "Great" is not a specification — it's an invitation for the model to pick the most common interpretation of great, which is, by definition, unremarkable.

Food for thought:

  • Count the decisions the agent made for you (colors, layout, interactivity, file structure…). If this were production work, how many of those would you have wanted to make yourself?

Step 2 — Same prompt, Plan mode

New folder, new chat. Switch the agent to Plan mode and paste the exact same prompt:

write a great hello world app in html

This time the agent must show you a plan before writing code. Your job:

  1. Read the plan. All of it — this is the step most people skip.
  2. Fix errors. Point out anything wrong, missing, or assumed. Reply in chat with your corrections and watch the plan change.
  3. Approve only when the plan says what you actually want, and let it execute.

The prompt is still lazy — but now there is a checkpoint between the request and the code, and you saw the agent's assumptions before they became files.

What Plan mode actually changes

Plan mode splits one bundled job into two: decide what to build, then build it. This is the pipeline principle — one cognitive task per step. When a model plans and executes in a single pass, it commits to its first idea and rationalizes it while building. The split lets you inspect (and correct) the thinking before it hardens into code — the cheapest moment to fix anything.

Food for thought:

  • Compare the Step 1 and Step 2 results. Same prompt, same model — where did the improvement come from?
  • What assumptions survived into the plan that you only caught because you read it?

Step 3 — Human structured plan-based prompt

New folder, new chat, Plan mode. Now use a prompt written by a human who has been burned before: it raises the bar ("epic", "memorable"), constrains the output (self-contained), and gives the plan itself rules — diagrams, tasks with dependencies, a verification gate, step-by-step commits, and mandatory questions:

create an epic "hello world" in html. It must be memorable, interactive, but formal and professional. Rich-content, self-contained.

Follow these rules:

- add the user's prompt to the plan, using markdown quote syntax >. If there're plan corrections, and them as well
- add diagrams to the plan: add mermaid diagrams to explain the architecture, user flow (sequence diagram), or any other information that is not obvious. DO NOT add mermaid diagrams to the final html.
- add tasks with dependencies to the plan. Use your task/todo tracking tool
- add verification gate to the plan: you must write validation tasks to confirm live if the result is correct. Use a heaful browser, I want to watch how you run these tests
- commit the resulting files step by step in a brand-new local repo

During the planning session, ask me anything you need to do a GREAT JOB. You can add follow-up questions if my answer is not clear or is inconsistent. Don't assume anything.

Then follow the same routine as Step 2: answer its questions, read the plan, fix errors, approve — and this time, watch the verification tasks run in the visible browser.

What this prompt already does well — and where it's weak

Well: it forces questions ("ask me anything… don't assume"), demands a verification step with observable evidence (headful browser), makes work traceable (quoted prompt, tasks with dependencies, atomic commits), and keeps diagrams where they belong (the plan, not the product).

Weak: "epic yet formal and professional" is a tension with no arbiter — who decides what qualifies? And most instructions are rules, not gates: "you must verify" has an opt-out path a model can rationalize ("it clearly works, no need"). A gate would block progress until objective evidence exists. Keep this critique in mind — Steps 4 and 5 attack exactly these weaknesses.

Food for thought:

  • Which of the six rules changed the output most? Which changed it least?
  • The prompt says "Don't assume anything." Did the agent still assume things? How would you make that instruction impossible to ignore?

Step 4 — Meta-prompted

If prompts drive quality, why write them by hand? In this step the agent optimizes its own prompt. New chat (normal agent mode is fine for the rewrite). Paste this meta-prompt, which contains the Step 3 prompt inside:

You are an expert prompt engineer. Rewrite the prompt below to get the best possible result from an AI coding agent working in Plan mode. You may restructure it completely, but keep every requirement it contains. Return ONLY the rewritten prompt, ready to paste.

--- PROMPT TO REWRITE ---
create an epic "hello world" in html. It must be memorable, interactive, but formal and professional. Rich-content, self-contained.

Follow these rules:

- add the user's prompt to the plan, using markdown quote syntax >. If there're plan corrections, and them as well
- add diagrams to the plan: add mermaid diagrams to explain the architecture, user flow (sequence diagram), or any other information that is not obvious. DO NOT add mermaid diagrams to the final html.
- add tasks with dependencies to the plan. Use your task/todo tracking tool
- add verification gate to the plan: you must write validation tasks to confirm live if the result is correct. Use a heaful browser, I want to watch how you run these tests
- commit the resulting files step by step in a brand-new local repo

During the planning session, ask me anything you need to do a GREAT JOB. You can add follow-up questions if my answer is not clear or is inconsistent. Don't assume anything.

Read the rewritten prompt the agent gives you. Then: new folder, new chat, Plan mode, paste the agent-optimized prompt, and follow the usual routine — questions, read, fix, approve.

What meta-prompting can and cannot do

The model has read millions of prompts and knows the folk wisdom: structure, explicit constraints, roles, numbered phases. Expect the rewrite to be tidier and more complete than the human version.

But it optimizes from intuition, not evidence. It typically won't know that commitment-first raises compliance measurably, that exactly one emotional stimulus helps but stacked ones don't, that chain-of-thought hurts certain task types, or that a rule only becomes reliable when converted into a gate with artifact evidence. Intuition gets you a better prompt; evidence gets you a different class of prompt. That gap is Step 5.

Food for thought:

  • Diff the agent's rewrite against the Step 3 original. What did it add on its own? Did it drop or weaken any of your six rules?
  • Would you have accepted this prompt from a colleague? What's still missing?

Step 5 — Meta-prompted with rules

Same idea as Step 4, with one decisive change: instead of letting the agent improvise from intuition, you hand it a machine-readable optimization spec — prompt-optimization-context.md — where every practice is a numbered section (S1–S9) backed by a verified reference [Rn]. The agent must follow the spec's process: apply the sections in order, respect the caveats, and pass the final emission checklist before it is allowed to output anything.

New chat. Attach prompt-optimization-context.md to the context and paste:

Optimize the prompt below by following the process encoded in @file:prompt-optimization-context.md — apply sections S1 through S9 IN ORDER, respect every CAVEAT, and emit only after every box in the §S9 emission gate is checked. Return ONLY the optimized prompt, ready to paste into a coding agent in Plan mode.

What a spec-optimized prompt looks like

Below is the prompt this process produced when we ran it. Compare it with what your run generates — the wording will differ, the structure shouldn't.

💡 Every dotted-underlined passage is clickable — it opens a popup naming the practice, the mechanism, and the measured evidence behind it.

ROLE: You are a senior creative technologist and front-end engineer known for award-winning single-page experiences. This page opens a live corporate training session, so a memorable first load is critical.

REFERENCE — original request:
> create an epic "hello world" in html. It must be memorable, interactive,
> but formal and professional. Rich-content, self-contained.

CONSTRAINTS:
- One self-contained .html file: inline CSS/JS, zero external dependencies. Must render identically offline.
- Formal, professional aesthetic: restrained palette, strong typographic hierarchy. Memorable through craft and motion, not gimmicks.
- Semantic HTML5, WCAG 2.1 AA contrast, prefers-reduced-motion respected, responsive 360px→4K, zero console errors or warnings.

PROCESS — execute phases in order; do not skip ahead:
Phase 1 · CRITERIA: State the criteria an excellent result must meet across memorability, interactivity, professionalism, technical quality. Every later phase is judged against these.
Phase 2 · CONCEPTS: Generate 3 distinct design concepts. Evaluate each against the Phase 1 criteria. Select the strongest; justify the choice.
Phase 3 · ANTI-VERSION: List the flaws of the worst plausible "hello world" (clichés, gimmicks, accessibility failures). The final page must avoid every listed flaw.
Phase 4 · BUILD: Implement the selected concept thoroughly and in great detail.
Phase 5 · VERIFY (gate): Open the page in a headful browser → exercise every interactive element → capture screenshot + console output → gate clears only when the screenshot shows the rendered page AND the console shows zero errors/warnings. Not cleared → fix and re-run; do not proceed.
Phase 6 · REVIEW: Review the page with fresh eyes, as a reviewer who did not build it. List concrete weaknesses vs Phase 1 criteria — a weakness without a specific element reference doesn't count. Fix each; re-run Phase 5.

You have unlimited time and resources; optimize for craft and completeness, not speed.

Task graph — dependencies and the gate loop

This is the shape of the plan that prompt produces. Each task is one cognitive job with explicit blockers; the orange node is the verification gate — dashed orange edges are the fail-and-fix loop (draft → critique → revise, repeated until the gate clears).

Why a spec beats intuition

The spec encodes what the research actually measured, including the counter-intuitive parts a meta-prompt won't guess: stating criteria before producing (commitment, the strongest compliance lever measured), exactly one emotional-stakes sentence (stacking adds nothing), no chain-of-thought on aesthetic judgment (it measurably hurts), reference material at the top and instructions at the end (mid-context content gets lost), and every rule converted into a gate that demands an artifact — a screenshot, a console log, a count — never a self-assessment.

It also encodes anti-patterns: things a well-meaning optimizer would add that make prompts worse. Constraints are as valuable as techniques.

Food for thought:

  • Diff your Step 5 prompt against your Step 4 prompt. Which differences came from evidence the model couldn't have intuited?
  • The spec forbids some things (CoT on intuitive tasks, stacked emotional stimuli, decorative personas). Did your Step 4 rewrite commit any of these anti-patterns?

If something breaks

  • No Plan mode in your Copilot → update the extension; if it's still missing, prepend "First present a detailed plan and WAIT for my explicit approval before writing any file" to the prompt — a manual plan gate.
  • The agent skips its questions and starts planning → interrupt and reply: "You skipped the questions. Ask them first." It complies.
  • The headful browser never appears (Step 3 onward) → the agent probably lacks a browser tool (e.g. the Playwright MCP server). Ask it: "What tool will you use to open a visible browser? If none, say so in the plan."
  • Step 5: the agent ignores the spec file → verify the file is really attached to the chat context (the @file: reference must resolve); if in doubt, paste the spec's content directly into the chat before the prompt.
  • Results look suspiciously similar between steps → you probably reused a chat session or folder. Fresh chat, fresh folder, re-run.
  • Golden rule: change one thing at a time — that's the whole point of the ladder.
