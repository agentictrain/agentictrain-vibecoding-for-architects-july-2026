Spec-first mini-build: portfolio explorer

Participant guide — one CSV, one spec, one double-clickable page

You have application-portfolio.csv — 40 fictional applications at NorthGrove Foods. You will build a web page your team could use to explore this portfolio, writing the spec first and letting Copilot build it. No code, no installation: the result is a single HTML file you open in your browser.

Done when you have:

  • spec-001.md — one page: goal, features in scope, out of scope, 3 acceptance criteria — immutable once approved
  • spec-002.md — the Step 5 change, in its own spec file (later requirements never rewrite spec-001.md)
  • A working double-clickable HTML page built exactly to those specs
  • A git history with ≥2 commits made by the agent

Setup

Open this folder in VS Code, open Copilot Chat, and switch the mode to Agent. The working folder is the one containing instructions.md and application-portfolio.csv.

Folder: day-1/exercise-portfolio-explorer
Chat mode: Agent

Step 1 — The interview

Do not describe the whole solution. Make the agent interview you:

I want a single, self-contained HTML file (no server, no installation —
I will double-click it in my file explorer) that lets my team explore
the application portfolio in application-portfolio.csv.

Before building anything, interview me: ask me up to 6 questions, one
at a time, about what the page must show and do. Then write spec-001.md —
one page: goal, features in scope, out of scope, and 3 acceptance
criteria phrased as "I can …". Wait for my approval before building.

Answer as the architect you are — think about who would use this page and for what (cost review? rationalization candidates? criticality overview?).

If the agent skips the interview and starts building, stop it: "You skipped the interview. Ask your questions first."

Step 2 — Approve the spec

Read spec-001.md. Cut anything you don't need (say so in chat — the agent updates the file). This review is the only time spec-001.md changes: once you approve it, it is immutable, and every later requirement will get its own numbered spec file. When it matches what you meant:

Approved. Build it exactly to spec-001.md. Embed the CSV data inside the
HTML file so it works with a double-click, offline. When done, tell me
how to open it and check each acceptance criterion yourself.

Step 3 — Open and test

Open the HTML file: right-click it in the VS Code Explorer → Reveal in File Explorer / Finder → double-click. Then test your three acceptance criteria yourself — don't take the agent's word for it. Finally, make the agent prove one number on the page. The prompt below uses the total annual cost; if you'd rather check a different number, ask about that one instead:

Prove that the total annual cost shown on the page is correct by
computing it directly from application-portfolio.csv and showing me
the calculation.

Step 4 — Checkpoint with git

You will never type a git command in this course — the agent drives:

Initialize a git repository in this folder and commit everything with
the message "checkpoint: first working version". Show me the result.

If it reports an identity error, tell it: "Configure a local git user name and email for this repository first, then commit."

Step 5 — One change, spec first

Pick one improvement (a filter, a chart, a sort). spec-001.md is approved and therefore frozen — the new requirement goes in its own file. First have the agent write spec-002.md, approve it, then build it. The prompt below uses a chart as the improvement — swap in a filter or a sort if that fits your page better:

spec-001.md is approved and immutable — do not modify it. Write
spec-002.md describing exactly one change on top of it: a bar chart
of total annual cost per business domain. Show me spec-002.md and
wait for my approval before building. Once I approve, implement
exactly that change and commit with a message describing it.
Why immutable specs?

The same reason ADRs are never rewritten: an approved spec is a record of what was agreed, and the numbered files on top of it are the change history. If spec-001.md kept absorbing every new idea, you could no longer tell what was originally approved, what changed, or in which commit. One file per requirement also gives the agent a small, unambiguous work order — "implement spec-002.md" is harder to misread than "implement the new parts of spec-001.md".

Done criteria

You are done when the approved spec is intact, the Step 5 change has its own spec file, the page works offline with a double-click, and the agent has made at least two commits.

Extra Step 2 — Keep the CSV as an external source

The CSV gets updated weekly. With the data embedded, someone has to rebuild the page every week. Ask the agent to keep application-portfolio.csv as an external source instead — spec first, as always:

The portfolio CSV is updated weekly, so embedding the data means
rebuilding this page every week. Without modifying any existing spec
file, write spec-003.md: the page must read application-portfolio.csv
as an external file and parse it when the page loads. Show me
spec-003.md and wait for my approval before building. Once I approve,
implement it — and tell me honestly whether this will still work when
I double-click the HTML file. If not, explain why and list my options.
Spoiler — can the JS read the CSV when the page loads?

Not from a double-click. A page opened from the file system runs on the file:// scheme, where browsers block fetch() and XMLHttpRequest to other local files for security reasons. The same page works fine when served over HTTP.

So this is a requirements conflict, not a coding problem: "no server, double-click" and "always-fresh external data" cannot both hold. Typical options the agent should surface:

  • Serve the folder over HTTP (a tiny local server, or host it on the intranet)
  • Keep double-click and add a file picker or drag-and-drop so the user loads the weekly CSV manually
  • Keep embedding and re-run the build prompt weekly

Watch whether the agent tells you this before building or only after the page breaks — and notice that the resolution belongs in a spec file, not in the code.

If your page now shows an error like: "Could not read application-portfolio.csv at page load. In some browsers, opening HTML with file:// blocks local CSV fetch for security reasons."

The code is fine — the browser is refusing. Pages opened with a double-click run on the file:// scheme, where JavaScript is blocked from reading other local files. In other words, spec-003.md ("read the CSV at page load") now conflicts with spec-001.md ("works with a double-click, offline") — and a spec conflict is resolved in the specs, not by patching code. Hand it back to the agent:

The page shows this error: "Could not read application-portfolio.csv
at page load. In some browsers, opening HTML with file:// blocks
local CSV fetch for security reasons." Explain the cause, then list
my options with their trade-offs. Do not modify any existing spec
file. When I pick an option, write spec-004.md for it, show it to me,
and wait for my approval before building.
